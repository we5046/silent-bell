# 울리지 않는 종탑: 2~4인 협동 던전 설계 v1

- 작성일: 2026-09-26
- 세계관: 「노래」 시리즈 (`D:\pixel\story\00_세계관.md`, 1장 설계 `01_프롤로그_1장.md`)
- 목적: 게임 서버 포트폴리오. 목표 직군은 중소 게임사 서버 개발자이며, **완성도와 리눅스 배포 경험**을 우선한다.

---

## 1. 게임 개요

- 2~4명이 한 방에 모여 던전 하나를 공략하는 협동 액션이다.
- 형식은 **벨트스크롤**(마스터 오브 판타지 방식)이다. 캐릭터는 옆모습이고 배경은 쿼터뷰로 그린다. 좌우 이동과 깊이(화면 위아래) 이동이 있으며 점프는 없다.
- 클래스는 검사·마법사·궁수·바드 4종이다. **한 방 안에서 클래스는 중복될 수 없다.** 클래스마다 남·여 외형이 있고, 외형은 성능에 영향을 주지 않는다.
- 세계관 연결: 검(몸의 노래), 마법사(말의 노래, 언령), 궁수(활의 노래), 바드. 던전은 침묵 지대이고, 최종 목표는 정지핵(울리지 않는 종)을 파괴하는 것이다.

## 2. 기술 구성

| 영역 | 선택 |
|---|---|
| 서버 | C# .NET 10 콘솔 앱. `System.Net.Sockets` 위에 세션, 패킷 조립, 방 관리를 직접 구현한다. ASP.NET이나 SignalR은 쓰지 않는다 |
| 전송 | TCP. 패킷 형식은 `[길이 2바이트][패킷 ID 2바이트][Protobuf 본문]`이다. 길이는 헤더를 포함한 전체 바이트 수이고, 리틀 엔디언이다 |
| 직렬화 | Protobuf (`proto/packets.proto`가 단일 원본). 이 파일에서 C# 코드를 생성해 `shared/Generated/`에 둔다 |
| 공유 코드 | `shared/`(.NET Standard 2.1). 서버와 Unity가 같은 소스를 쓴다 |
| 클라이언트 | Unity 6 (6000.3.23f1), 2D URP, Windows PC 빌드 |
| 배포 | AWS EC2 서울 리전, Ubuntu 24.04 LTS, `t4g.small`, systemd |
| 제외 | DB, 계정, 재접속, UDP, 채팅, 사운드, Docker (2단계 후보) |

## 3. 저장소 구조

```

├─ shared/                    .NET Standard 2.1. Unity 로컬 패키지를 겸함 (package.json + asmdef)

│   └─ Rules/                 수치, 맵 경계, 이동 계산 (서버와 클라이언트가 공유)

├─ server.tests/              xUnit
├─ tools/bot/                 콘솔 봇 클라이언트 (테스트와 부하 측정용)
├─ client/                    Unity 프로젝트. Packages/manifest.json에서 "file:../../shared"로 참조
├─ deploy/                    systemd 유닛, deploy.ps1
└─ docs/
```

- Unity에서 쓸 `Google.Protobuf.dll`(netstandard2.0)은 `client/Assets/Plugins/`에 둔다.

### 2-1. 패킷 형식을 이렇게 정한 이유

| 선택 | 이유 |
|---|---|
| 앞에 길이를 붙임 | TCP는 메시지 경계가 없는 바이트 스트림이다. 보낸 패킷이 붙어서 오거나 잘려서 올 수 있으므로 "어디까지가 한 패킷인지" 표시가 필요하다. 구분 문자는 바이너리 본문과 충돌하고, 고정 크기는 대역폭을 낭비한다 |
| 길이 2바이트 | 최대 65,535바이트로 충분하다(가장 큰 스냅샷도 개체 50개 기준 1~2KB). 4바이트면 악의적인 거대 길이 값으로 서버에 큰 버퍼를 잡게 만들기 쉽다. 여기에 4KB 상한을 추가로 검사한다 |
| 길이에 헤더 포함 | 수신 버퍼에 "길이만큼 쌓였는가"만 확인하면 되므로 조립 코드가 단순하다. 최소 유효 길이는 4다 |
| 패킷 ID를 헤더에 분리 | Protobuf 바이트는 자기 타입을 담고 있지 않아서, 파싱 전에 타입을 알아야 한다. ID로 처리 함수 표를 바로 찾고, 현재 상태에서 허용되지 않는 패킷(예: 로비에서 보낸 게임 입력)은 파싱 없이 버린다. 대안인 `oneof` 봉투 메시지보다 업계에서 흔한 방식이다 |
| 리틀 엔디언 | 서버(ARM)와 클라이언트(x86)가 모두 리틀 엔디언이라 변환이 필요 없다. 양쪽 모두 `BinaryPrimitives`로 명시적으로 읽고 쓴다 |

## 4. 서버 구조

### 4-1. 스레드 모델

```
[Accept 루프]      → Session 생성, 로비에 등록
[Session 수신]     async 소켓 (리눅스에서는 epoll, Windows에서는 IOCP를 런타임이 선택)
                   수신 버퍼 → 길이 헤더로 패킷 조립 → 소속 큐(로비 또는 방)에 넣음
[Lobby 루프]       로비 큐를 처리: 로그인, 방 생성·참가, 클래스 선택, 준비, 시작
[Room 틱 루프]     방마다 1개, 20Hz (50ms)
                   큐의 입력 처리 → 게임 로직 → S_Snapshot 전송
[Session 송신]     세션별 송신 큐. 동시에 진행되는 전송은 하나뿐이다
```

- **게임 로직은 방 틱 루프 한 곳에서만 실행된다.** 네트워크 스레드는 `ConcurrentQueue`에 넣기만 하므로 게임 로직에는 락이 없다.
- 세션이 방에 들어가면 이후 패킷의 목적지가 해당 방의 큐로 바뀐다.
- 게임 로직은 `Step(dt, inputs)` 형태의 순수 로직으로 두어, 소켓 없이 테스트할 수 있게 한다.
- **틱은 항상 고정 dt(0.05초)로 계산한다.** 서버가 잠깐 멈췄다가 재개되면 밀린 틱을 고정 dt로 따라잡되, 한 번에 최대 5틱까지만 처리하고 나머지는 버린다. 실제 경과 시간을 dt로 쓰면 게이지나 이동이 한 번에 크게 튀기 때문이다.

### 4-1-1. 입력 처리와 통신 지연

- 방은 플레이어마다 **가장 최근 입력 상태**(이동 방향)와 **아직 처리하지 않은 버튼 누름**(공격, 기술, 구르기)을 보관한다.
- 한 틱에는 가장 최근 이동 방향만 적용한다. 입력이 몰려 도착해도 이동을 한꺼번에 적용하지 않으므로 순간이동이 생기지 않는다. 버튼 누름은 누락되지 않도록 모아 두었다가 차례로 처리한다(쿨다운 검사는 그대로 적용).
- 마지막 입력을 받은 뒤 **250ms까지는 그 입력을 유지**한다.
- 250ms가 지나도록 입력이 없으면 **통신 지연** 상태로 본다. 이동은 멈추고, **침묵 게이지도 오르거나 내리지 않고 그대로 둔다.** 입력이 다시 오면 정상 계산으로 돌아간다. 통신 지연 중에도 피격은 정상 처리한다.

### 4-2. 패킷

| 방향 | 패킷 | 내용 |
|---|---|---|
| C→S | `C_Login` | 닉네임 |
| S→C | `S_LoginResult` | 로그인 성공 시에만 보냄. 내 플레이어 ID. 실패는 `S_Error`로 보낸다 |
| C→S | `C_CreateRoom` / `C_JoinRoom` | 방 코드 (참가 시) |
| S→C | `S_RoomState` | 방 코드, 방장 ID, 슬롯 목록(닉네임, 클래스, 성별, 준비 상태). 변경될 때마다 전원에게 보냄 |
| S→C | `S_Error` | 거절 사유 코드. **모든 요청 거절(로그인 실패 포함)은 이 패킷 하나로** 보낸다 |
| C→S | `C_PickClass` | 클래스, 성별 |
| C→S | `C_Ready` / `C_StartGame` / `C_LeaveRoom` | |
| S→C | `S_GameStart` | 구간 정보, 개체 초기 상태 |
| C→S | `C_Input` | 입력 번호(seq), 이동 방향(x, y), 버튼 비트(공격, 기술, 구르기, 부활) |
| S→C | `S_Snapshot` | 틱 번호, 모든 개체(ID, 종류, 위치, 방향, 체력, 상태, 침묵 게이지, 클래스, 성별), 내 마지막 처리 seq, 현재 구간 |
| S→C | `S_Event` | 피격, 쓰러짐, 부활, 굳음, 기믹 작동, 구간 이동, 그로기, 전멸, 승리 |
| S→C | `S_Result` | 클리어 시간, 플레이어별 부활 횟수와 가한 피해 |

### 4-3. 검증 원칙

- 클라이언트는 **입력만** 보낸다. 위치, 속도, 쿨다운, 명중, 피해, 기믹, 승패는 모두 서버가 계산한다.
- 이동 방향 벡터는 서버에서 길이를 1 이하로 제한한다.
- 닉네임은 2~12자로 제한하고, 접속 중인 닉네임과 중복되면 거절한다. 패킷 길이가 상한(4KB)을 넘거나 알 수 없는 패킷 ID가 오면 연결을 끊는다.

### 4-4. 오류 처리와 로그

**요청 거절**: 규칙에 맞지 않는 요청은 모두 `S_Error { ErrorCode }`로 거절한다. 거절 사유는 `ErrorCode` 하나에서 관리하고, 클라이언트는 이 코드를 메시지로 바꿔 보여 준다(7절).

**서버의 예외 경계** (예외를 잡는 곳은 세 군데뿐이다)

| 경계 | 처리 |
|---|---|
| Accept 루프 | 접속 하나에서 난 `SocketException`은 WARN 로그를 남기고 100ms 쉰 뒤 다음 접속을 계속 받는다. 그 밖의 예외는 로비 잡 큐를 멈춘 뒤 위로 던져 프로세스를 종료한다. systemd가 재시작한다 |
| 세션 | 수신 중 어떤 예외든(규약 위반 포함) 그 세션만 닫는다. 다른 세션과 로비에는 영향이 없다 |
| 잡 큐 | 잡 하나에서 난 예외는 ERROR 로그를 남기고 다음 잡을 계속 처리한다 |

- 서버가 조용히 멈춘 채 살아 있는 상태(접속은 못 받는데 프로세스는 살아 있음)를 만들지 않는다. 복구할 수 없으면 종료해서 systemd가 재시작하게 한다.

**로그 형식**: 모든 로그는 표준 출력 한 곳으로 보내고 형식을 통일한다. systemd가 `journalctl`로 모은다.

```
2026-09-26 21:04:11.532 [WARN ] accept     ConnectionReset ...
2026-09-26 21:04:15.018 [INFO ] session    7 connected 1.2.3.4:51234
2026-09-26 21:05:02.771 [ERROR] job        System.NullReferenceException ...
```

## 5. 로비

1. **접속**: 서버 주소(기본값 내장, 수정 가능)와 닉네임을 입력한다.
2. **메인**: 방 만들기를 누르면 서버가 방 코드 4자리를 발급한다(영문 대문자와 숫자, 0/O/1/I 제외). 코드로 참가할 수도 있다. 방이 없거나, 4명이 찼거나, 이미 시작했으면 거절한다.
3. **대기실**
   - 캐릭터 카드 8장(4클래스 × 남·여)을 처음부터 보여 준다. 카드 하나를 고르면 `C_PickClass { 클래스, 성별 }`을 보낸다.
   - 클래스는 먼저 요청한 사람이 선점한다. 이미 다른 사람이 가진 클래스를 요청하면 거절한다. 누군가 검사(여)를 고르면 검사(남) 카드도 함께 잠긴다.
   - 준비는 클래스를 고른 뒤에만 켤 수 있다. 준비 버튼을 누르면 "준비 해제" 버튼으로 바뀐다.
   - **준비 상태에서는 캐릭터(클래스와 성별)를 바꿀 수 없다.** 서버는 준비 상태에서 온 `C_PickClass`를 `AlreadyReady`로 거절한다. 바꾸려면 먼저 준비를 해제한다.
   - 방장은 먼저 들어온 사람이다. 방장이 나가면 다음으로 들어온 사람이 이어받는다.
   - 시작 조건: 2명 이상, 전원 클래스 선택과 준비 완료. 방장만 시작할 수 있다.
4. **던전**을 진행한 뒤 **결과 화면**을 거쳐 대기실로 돌아온다. 준비 상태는 초기화된다.

## 6. 게임 규칙

### 6-1. 좌표와 판정

- 바닥 좌표는 `x`(좌우)와 `y`(깊이)이고, 단위는 픽셀이다.
- 명중 조건: 공격 범위와 x 구간이 겹치고, **깊이 차이가 ±12px 이내**여야 한다.
- 구간마다 걸을 수 있는 사각 경계를 `shared/Rules`에 수치로 정의한다. 서버와 클라이언트가 같은 값을 쓴다.

### 6-2. 클래스 (초기값, `shared/Rules`에서 조정)

| 클래스 | 체력 | 기본 공격 | 고유 기술 |
|---|---|---|---|
| 검사 | 200 | 3타 콤보 10/10/20, 사거리 40 | 안개 가르기: 120px 돌진, 경로상의 적에게 30 피해, 쿨 6초 |
| 마법사 | 110 | 마력탄 18 (초속 200, 관통 없음) | 명각: 100px 앞 반경 60 결계, 4초간 안의 적 50% 둔화, 쿨 10초 |
| 궁수 | 90 | 화살 12 (초속 500) | 부름 화살: 관통, 35 피해, 넉백 60px, 쿨 7초 |
| 바드 | 120 | 음파 8, 사거리 60 | 노래: 반경 150 안의 아군 40 회복, 굳음 해제, 5초간 부활 속도 2배, 쿨 15초 |

- 공통 구르기: 0.4초 이동, 그중 처음 0.3초는 무적이다. 쿨 1초.
- 공통 이동 속도: 초당 120px.

### 6-3. 침묵 (굳음 게이지 0~100)

- 게이지는 **0~100 사이로 제한한다.** 0 아래로 내려가지 않으므로, 오래 움직여 여유를 쌓아 둘 수 없다.
- 이동도 공격도 하지 않은 틱에는 초당 +20(틱당 +1), 행동한 틱에는 초당 -60(틱당 -3)이 적용된다. 행동은 이동 입력, 공격, 기술, 구르기, 부활 입력을 말한다.
- 0에서 굳음까지는 가만히 5초가 걸린다.
- 50 이상이면 이동 속도가 줄어든다. 50일 때 100%, 100 직전에 50%가 되도록 선형으로 감소한다.
- 100에 도달하면 **굳음** 상태가 되어 조작할 수 없다. 동료의 공격에 맞거나(피해 없음) 바드의 노래를 받으면 게이지 0으로 풀린다.
- 3구간(침묵의 벽)에서는 상승 속도가 **2배**다(가만히 2.5초면 굳음).
- 통신 지연 상태(4-1-1)에서는 게이지를 변경하지 않는다.
- 굳음은 죽음이 아니다. 전멸 판정에만 영향을 준다.

### 6-4. 쓰러짐, 부활, 전멸

- 체력이 0이 되면 쓰러진다. 동료가 40px 안에서 부활 입력을 3초 유지하면 체력 30%로 일어난다. 노래 효과 중에는 1.5초다.
- 살아서 행동할 수 있는 플레이어가 없으면(모두 쓰러지거나 굳음) **전멸**이다. 5초 뒤 현재 구간의 시작 상태로 되돌린다. 몬스터와 기믹은 초기화하고, 플레이어는 체력을 모두 회복한다. 재도전 횟수는 제한하지 않는다.

### 6-5. 인원 보정

- 계수 `k = 0.5 + 0.25 × 시작 인원` (2명 1.0, 3명 1.25, 4명 1.5)
- 몬스터 체력과 웨이브 수에 `k`를 곱한다. 발판과 공명석 개수는 시작 인원과 같다.
- 도중에 연결이 끊겨도 `k`와 기믹 개수는 시작 인원 기준을 유지한다.

### 6-6. 몬스터

- **잔재(소)**: 체력 30, 가장 가까운 플레이어를 추적해 근접 공격한다(피해 8).
- **잔재(대)**: 체력 90, 1초 멈췄다가 직선으로 돌진한다(피해 20). 벽이나 끝에 닿으면 멈춘다.

### 6-7. 구간

| 구간 | 조건 |
|---|---|
| 1. 잿빛 광장 | 잔재 웨이브 3번을 모두 처치하면 통과 |
| 2. 멈춘 사람들의 거리 | 발판 N개가 **동시에 3초** 눌리면 문이 열린다. 그동안 잔재가 계속 등장한다 |
| 3. 종탑 계단 | 침묵 2배 구간. 한 명이라도 오른쪽 끝에 도착하면 전원을 다음 구간으로 옮긴다. 잔재는 적게 등장한다 |
| 4. 울리지 않는 종 | 보스를 처치하면 승리 |

- 구간이 진행 중일 때는 화면과 이동 경계가 해당 구간으로 잠긴다.

### 6-8. 보스: 울리지 않는 종

- 체력: 3000 × k
- **파문**: 4초마다 종을 중심으로 타원형 고리가 퍼진다. 고리 테두리와 겹치는 순간 15 피해를 받는다. 구르기 무적 중에는 무시한다.
- **소환**: 12초마다 잔재(소) 3마리를 부른다.
- **2페이즈** (체력 50% 이하): 파문이 두 겹으로 퍼지고 주기가 2.5초로 줄어든다.
- **그로기**: 30초마다 경기장에 공명석 N개(체력 40)가 나타난다. 5초 안에 모두 깨면 종이 8초 동안 멈추고 받는 피해가 2배가 된다. 실패하면 모든 플레이어에게 25 피해를 주는 큰 파문이 퍼진다.
- 처치하면 `S_Event(Victory)`를 보내고, 종이 마지막으로 한 번 울리는 연출을 재생한 뒤 결과 화면으로 넘어간다.

### 6-9. 연결 끊김

- 끊긴 플레이어의 캐릭터는 즉시 방에서 제거한다. 재접속은 지원하지 않는다.
- 대기실에서 끊기면 슬롯과 클래스를 해제한다. 방이 비면 삭제한다.

## 7. 클라이언트 (Unity)

- 씬은 `Lobby`(접속, 메인, 대기실)와 `Dungeon` 두 개다.
- `NetworkClient` 싱글톤은 `DontDestroyOnLoad`로 유지한다. 수신 스레드가 패킷을 큐에 넣고, 메인 스레드의 `Update`에서 꺼내 처리한다.
- **다른 개체**: 100ms 늦게 그리며 두 스냅샷 사이를 보간한다.
- **내 캐릭터**: 입력 즉시 `shared/Rules`의 이동 계산으로 먼저 움직인다. 스냅샷을 받으면 서버 위치에서 시작해, 마지막으로 처리된 seq 이후의 입력을 다시 적용해 보정한다.
- 화면: 기준 해상도 480×270, Pixel Perfect Camera, 화면 아래쪽 개체가 앞에 오는 Y축 정렬을 쓴다.
- UI: uGUI, 한글 폰트는 갈무리(OFL).
- 조작: 방향키 이동, Z 공격, X 기술, C 구르기, Space를 길게 눌러 부활. 굳은 동료는 공격으로 깨운다.
- HUD: 상단에 파티원 체력바, 하단에 내 기술 쿨다운, 침묵 게이지(화면 가장자리의 잿빛 비네트), 쓰러진 동료 위에 부활 진행 원을 표시한다.

### 7-0. 오류 표시와 시간 제한

- 모든 실패는 **오류 팝업 하나**로 보여 준다. 서버가 보낸 `ErrorCode`와 클라이언트 자체 오류를 한 표에서 한국어 메시지로 바꾼다.
- 서버가 접속 자체를 받지 못한 경우(Accept 실패)에는 클라이언트에 알릴 통로가 없다. 그래서 클라이언트가 **스스로 시간 제한**을 둔다.

| 클라이언트 자체 오류 | 조건 | 메시지 | 다음 동작 |
|---|---|---|---|
| 연결 실패 | 5초 안에 TCP 연결이 안 됨, 또는 연결 거부 | "서버에 연결할 수 없습니다" | 다시 시도 버튼 |
| 응답 없음 | 요청(로그인, 방 생성·참가) 후 5초 안에 응답이 없음 | "서버 응답이 없습니다" | 연결을 닫고 다시 시도 버튼 |
| 연결 끊김 | 대기실이나 게임 중 소켓이 닫힘 | "서버와 연결이 끊어졌습니다" | 접속 화면으로 돌아감 |

- `ErrorCode` 메시지 예: `NicknameTaken` → "이미 사용 중인 닉네임입니다", `RoomFull` → "방이 가득 찼습니다", `AlreadyReady` → "준비를 해제한 뒤 캐릭터를 바꿀 수 있습니다".

### 7-1. 스프라이트

## 8. 배포

- EC2 `t4g.small`, Ubuntu 24.04 LTS, 서울 리전, 탄력적 IP.
- 보안 그룹: 22번은 개발자 IP만, 7777번(게임)은 전체에 연다.
- 빌드: `dotnet publish server -c Release -r linux-arm64 --self-contained`
- `deploy/deploy.ps1`: 빌드, scp 업로드, `systemctl restart silent-bell`을 한 번에 실행한다.
- `deploy/silent-bell.service`: `Restart=always`. 로그는 `journalctl -u silent-bell`로 본다.
- AWS Budgets 알림을 설정한다. 크레딧 만료일(2026-11-26) 전에 유료 전환이나 Lightsail 이전을 결정한다.
- 클라이언트: Unity Windows 빌드를 zip으로 배포한다.

## 9. 테스트

- `server.tests` (xUnit)
  - 패킷 조립: 한 패킷이 여러 번에 나뉘어 도착하는 경우, 여러 패킷이 한 번에 도착하는 경우, 상한을 넘는 길이, 4 미만의 길이

  - 로비: 닉네임 검증, 방 코드 발급, 가득 찬 방과 시작한 방 거절, 클래스 선점, 방장 승계, 시작 조건
